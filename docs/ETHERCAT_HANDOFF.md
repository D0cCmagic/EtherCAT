## 3. ⚠️ 平台限制与工程约束（**必须遵守，否则会搞坏东西**）

### 3.1 关于用户的工程

| 约束 | 说明 |
|---|---|
| **不要改动与 EtherCAT 无关的既有代码** | 该工程是在用的业务工程（SD 卡 + R900PNR Wi-Fi + 双 Bank OTA）。AI 只**新增**文件，未改动既有业务代码 |
| **新模块当前无调用方** | `Mcal_Esc_PowerUp()` / `App_Esc_Esm_Init()` / `App_Cia402_Init()` **均无人调用**，加入构建后**行为零变化** —— 这是刻意设计，硬件到手后再逐个接通 |
| **芯片关键事实** | N32H785**EC** 型号 `EC` = EtherCAT，**片内集成 ESC，挂 AHB9 总线，基地址 `0x400B0000`**（`ETHERCAT_BASE`）。**不需要外挂 LAN9252** |
| **调度模型** | 工程用 **不可抢占的协作式软定时器**（`Mcal_TimerTask`，5 个任务槽 10/20/50/200/300 ms）。**PDO 交换不能放任务槽**，必须用 ESC 中断（实时域） |
| **双核** | M7（600 MHz）+ M4。ESC 时钟门控可分核（`RCC_AHB9_PERIPHEN_M7_ESC` / `_M4_ESC`）。建议 M4 跑从站栈、M7 跑 FOC |
| **D-Cache** | M7 开了 D-Cache，核间共享内存/复位前需 `SCB_CleanDCache()`（工程已有先例） |

### 3.2 已核实的关键 SDK 事实（**17 项已逐条对照源码**）

| 事实 | 证据位置 |
|---|---|
| ESC 基地址 `0x400B0000` | `n32h7xx.h:2877,3081` |
| ESC Wrapper `0x400C0000` | `n32h7xx.h:3080` |
| ESC 中断 187/188/189/190 | `n32h7xx.h:348-351`（OPB / SYNC0 / SYNC1 / WRP） |
| ESC 时钟门控（可分核，含 LP） | `n32h7xx_rcc.h:804-807` |
| ESC 复位 `RCC_AHB9_PERIPHRST_ESC` | `n32h7xx_rcc.h:310` |
| ESC 内核时钟源（`SYSBUSDIV`/PLL1B/2B/3A/3C） | `n32h7xx_rcc.h:2012-2018` |
| `RCC_ConfigETHERCATKerClk()` | `n32h7xx_rcc.c:6733` |
| **内核时钟必须精确 100 MHz** | `n32h7xx_rcc.c:6731` 官方注释 |
| AHB9 时钟 = 系统总线时钟 | `n32h7xx_rcc.c:7766` |
| 总线时钟门控 `RCC_EnableCFG4PeriphClk1(AHB9BUS)` | `n32h7xx_rcc.c:6910`，`rcc.h:999` |
| **ESCSYSDIV 分频编码含特例** | `n32h7xx.h:6605-6614`：1/2/4/8/**16=7**/32/64/128/256/512 |

**推论（已写入文档）**：300 MHz 系统总线下 `SYSBUSDIV` 路线**凑不出 100 MHz**
（分频链只有 2 的幂），**必须用独立 PLL 输出 100 MHz 给 ESC 内核**。

### 3.3 ⚠️ 根本性未验证假设（**务必向用户复述**）

**已交付的 `App_Esc_Reg.h` 与 `App_Esc_Esm.c` 建立在一个假设上：**

> **N32H785 片内 ESC 的寄存器布局与 Beckhoff ET1100 兼容。**

**这个假设来自行业惯例，不是官方文档。** 事实依据：
- 所有片内集成 ESC 的 MCU（TI AM335x/AM64x PRU-ICSS、瑞萨 RZ/T 等）都沿用 ET1100 布局 —— **强惯例，非保证**
- 工程 SDK 里**没有任何 ESC 寄存器定义**可对照（已全库检索确认）
- 公开网络检索**未取得** N32H785 的 ESC 寄存器手册

**含义**：
- `App_Esc_Reg.h` 的寄存器偏移**必须逐条对照官方手册后才能上板**。文件里已用
  `[ET1100]` / `[VERIFY]` 标注置信度
- **但 ESM 状态机的逻辑结构**（状态跳转、错误码语义、看门狗语义、拒绝跳转的握手方式）
  **属于 ETG.1000 协议标准，不论寄存器怎么排都成立** —— 这是"与芯片无关、可长期复用"的部分
- 其他未验证假设：ESC 是否允许 8/16 位访问、中断 187~190 的实际触发源、端口数量与 MII/RMII 类型

**核对入口**：`ETHERCAT_FAE_QUESTIONS.md` 的 **P0 项 Q1.1 / Q1.2**。

## 4. 已修复的缺陷与已知残留（**勿"重新发现"**）

### 4.1 已修复

| # | 缺陷 | 修复方式 |
|---|---|---|
| 1 | `Esc_Esm_CheckDcSync()` **无条件要求 DC**，误伤不用分布式时钟的主站（永远进不了 OP，报 `0x0032`） | 改为**应用层声明**：hooks 表新增可选钩子 `uint8_t (*IsDcRequired)(void)`；为 NULL 时视为"不要求 DC" |
| 2 | 寄存器访问函数在 `App_Esc_Esm.c` 内**私有重复实现** | 抽出共享 `Mcal_Esc_Reg.c/.h`，补齐 **32/64 位**访问（DC 的 64 位系统时间 `0x0910` 必需） |
| 3 | Keil 工程文件里 `Mcal_Esc_Init.c` **重复登记** | 已删除重复条目 |
| 4 | `ESC_REG_BASE` 与 `Mcal_Esc_Init.h` 的 `ESC_BASE_ADDR` **重复定义同一地址**且无人使用 | 已删除 `ESC_REG_BASE`，注明基地址唯一来源是 `ESC_BASE_ADDR` |

### 4.2 残留风险（**必须在新机器上提醒用户**）

| 风险 | 说明 |
|---|---|
| **DC 默认宽松** | 因修复 #1 的默认值是"不要求 DC"，**若伺服依赖 DC 同步却忘了注册 `IsDcRequired` 钩子，DC 故障不会被 ESM 拦截**。伺服应用**必须实现该钩子并返回 1** |
| **`cia402_behaviour_check.c` 从未执行** | 含 20+ 项断言（完整使能序列 `0x0006→0x0007→0x000F`、快停、故障上升沿清除）。编译通过但**本机无 ARM 执行环境**。**用户应在 Keil Debug 中从 `main()` 调用一次 `Esc_Cia402_Behaviour_Check()`**，会打印 `ALL PASS` 或 `FAIL: <哪一项>` |
| **整工程链接未做** | 若本机为 MDK-Lite 授权，该工程（约 880 KB）会在链接期因 32 KB 上限失败，且该失败与本模块无关。**用户在 Keil 里按 `F7` 即可确认** |
